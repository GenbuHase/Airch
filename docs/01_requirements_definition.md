- **プロダクト名**: `airch` (Architecture as Code / Architecture for AI)
- **ドキュメントバージョン**: 1.0.0
- **ステータス**: Approved
- **作成日**: 2026-09-26

---

## 1. プロダクト概要 & ビジョン

### 1.1 背景と課題意識
近年、フロンティアLLM（Claude 3.7/Sonnet, GPT-5.6, Grok 4.5等）やCursor、Claude Code、GitHub Copilot、WindsurfなどのAIコーディングアシスタントが普及し、ソフトウェア開発におけるコード記述速度は飛躍的に向上しました。
しかしながら、AIエージェントによる開発規模が拡大するにつれて、以下の深刻な問題が顕在化しています。

1. **アーキテクチャ的エントロピーの増大**:
   AIモデルは局所的なタスク解決には優れているものの、プロジェクト全体のアーキテクチャ境界（レイヤー構造、禁止された循環参照、クロスインポート、命名規則）を自律的に維持することが難しく、放置すると数日でコードベースが無秩序化（スパゲッティ化）します。
2. **AI指示書の陳腐化と同期ズレ**:
   `.cursorrules` や `AGENTS.md`、`CLAUDE.md` などのAIガイドラインファイルを手動で保守すると、プロジェクトの設計変更と同期が取れなくなり、AIに誤った指示を与えてしまいます。
3. **ルール遵守を強制する仕組みの欠如**:
   自然言語によるプロンプトやルール定義だけでは、AI（および人間）がルールを遵守することを100%保証できません。CI/CDパイプラインによる静的・決定論的な境界検証（Structural Linting）が不可欠です。

### 1.2 `airch` のミッション
`airch` は **「Architecture as Code (AaC)」** を実現するTypeScript製の次世代CLIツールです。
単一のマニフェストファイル（`airch.yaml`）をプロジェクトアーキテクチャの **Single Source of Truth (SSOT)** と位置づけ、以下の2つの柱を提供します。

```text
                     ┌──────────────────┐
                     │    airch.yaml    │ (Single Source of Truth)
                     └────────┬─────────┘
                              │
             ┌────────────────┴────────────────┐
             ▼                                 ▼
   [ Generator Engine ]              [ Structure Linter ]
             │                                 │
             ▼                                 ▼
  AIコンテキスト自動生成             決定論的アーキテクチャ検証
  (AGENTS.md, .cursorrules etc.)     (Local CLI & CI/CD Pipeline)
```

1. **AIコンテキストの決定論的自動生成**: `airch.yaml` の定義から各種AIツール（Cursor, Copilot, Claude Code, Windsurf等）向けのコンテキストファイルを自動生成・同期。
2. **決定論的構造リントと境界検証**: ディレクトリ階層、ファイル命名規則、必須ファイルの存在、およびレイヤー間の依存関係（許可/禁止インポート）をASTレベルで検証し、CIパイプラインでアーキテクチャ違反を遮断。

## 2. ターゲットユーザー & ユースケース

### 2.1 ターゲットユーザー
- **リードエンジニア / ソフトウェアアーキテクト**: プロジェクトの設計原則を定義・強制し、チーム全体（人間およびAI）のコード品質と秩序を担保したいエンジニア。
- **AIネイティブな開発者**: Cursor, Claude Code, GitHub Copilot 等のAIエージェントをペアプログラマーとしてフル活用している開発者。
- **プラットフォームエンジニア / SRE**: モノレポや複数リポジトリ間で共通のアーキテクチャ規約を配布・自動検証したいエンジニア。

### 2.2 主要ユースケース

#### ユースケース 1: プロジェクト立ち上げとアーキテクチャ定義
- **アクター**: リードエンジニア
- **フロー**:
  1. 新規プロジェクトのルートで `airch init` を実行。
  2. 対話形式でフレームワーク（Next.js, Fastify等）とアーキテクチャパターン（Feature-Sliced Design, Clean Architecture, Layered MVC等）を選択。
  3. ベストプラクティスに基づいた初期 `airch.yaml` が生成される。
  4. 必要に応じてプロジェクト固有の境界条件や命名規則を調整。

#### ユースケース 2: AIエージェントとのコンテキスト同期
- **アクター**: 開発者
- **フロー**:
  1. `airch.yaml` に新しいレイヤーやルールを追加（または既存の変更）。
  2. `airch generate` を実行。
  3. `AGENTS.md`, `.cursorrules`, `.github/copilot-instructions.md` などのAI用ルールファイルが決定論的に一括更新される。
  4. AIエージェントが最新のアーキテクチャ規約を前提にコード生成を行う。

#### ユースケース 3: 開発中のローカル検証 & Pre-commit Hook
- **アクター**: 開発者 / Git Hook
- **フロー**:
  1. 開発者（またはAI）が機能コードを実装。
  2. コミット前またはIDE上で `airch check` がトリガーされる。
  3. Feature間での直接インポートや命名規則違反、必須ファイルの欠落が検出された場合、違反箇所と理由、修正ガイドがターミナルに表示される。
  4. `--fix` オプションが指定されている場合、命名不整合のリネームや必須テンプレートの生成を自動実行。

#### ユースケース 4: CI/CD パイプラインによるアーキテクチャ境界の強制
- **アクター**: CIシステム (GitHub Actions / GitLab CI)
- **フロー**:
  1. Pull Requestがオープンされる。
  2. CIジョブ内で `airch check --strict` が実行される。
  3. ルール違反が1件でもある場合、終了コード `1` でジョブが失敗し、PRマージがブロックされる。
  4. GitHub Actions Annotations や PRコメントへ具体的な違反行と修正指示が出力される。

#### ユースケース 5: ビジュアルダッシュボードによるアーキテクチャ探索とGUI編集
- **アクター**: 開発者 / アーキテクト
- **フロー**:
  1. `airch ui` を実行してローカルWebスタジオを起動（未初期化プロジェクトの場合は専用セットアップ案内画面が表示され、1クリックで初期化可能）。
  2. モジュール間の依存関係グラフと境界ルールをブラウザ上で視覚的に俯瞰。
  3. 違反インポート（赤色破線）をリアルタイムに確認し、該当コードをインライン調査。
  4. GUI上でノード間を接続・編集し、`airch.yaml` へ直接反映保存。

| **FR-1.2** | 設定の継承 (Extends) | 外部パッケージ（`npm`）やローカルファイル（`extends: "@company/airch-config"`）からの設定継承・マージをサポートする。 | P1 (Should) |

| :--- | :--- | :--- | :--- |
| **FR-2.1** | マルチターゲット出力 | `AGENTS.md`, `.cursorrules`, `.github/copilot-instructions.md`, `CLAUDE.md` をサポート。 | P0 (Must) |

| **FR-3.4** | 依存関係・インポート境界検証 | ソースコードのASTを解析し、`import` / `require` / `export from` が `allowed_imports` / `forbidden_imports` に違反していないか検証する。 | P0 (Must) |

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1 実行速度 & 軽量性 (Performance & Efficiency)
- **スキャン速度**: 数千ファイル規模のプロジェクト（10,000ファイル・100万行）において、フルスキャン・リントが **2秒以内** に完了すること。
- **差分スキャン速度**: `--changed-only`（Git差分）による検証時は **200ms以内** に完了すること（Git pre-commit hook でストレスを感じさせないこと）。
- **メモリ消費量**: 大規模AST解析時でもピークメモリ使用量を **250MB以下** に抑制すること。

### 4.2 ゼロ・ランタイムオーバーヘッド (Zero Runtime Overhead)
- `airch` は純粋な開発時ツール（DevTool）およびCIパイプラインツールとして動作する。
- アプリケーションのランタイム依存（プロダクションコード）に一切の影響を与えないこと。
- インストールは `devDependencies`、実行は `npx airch` または `bunx airch` / `pnpm dlx airch` を基本とする。

### 4.3 厳格な型安全性 & 開発者体験 (Strict Typing & DX)
- TypeScript Strict モード（ES2024 / NodeNext モジュール解決）で完全実装。
- ユーザー向けに JSON Schema（`airch.schema.json`）を公開し、VSCodeやIntelliJ等のIDE上で `airch.yaml` 編集時に自動補完とリアルタイムバリデーションを提供。
- エラー出力は具体的かつ行動可能（Actionable）であること（違反ファイル、行・列番号、違反理由、許可されているモジュールの提示）。

### 4.4 決定論性と冪等性 (Determinism & Idempotency)
- 同一の `airch.yaml` とソースツリーからは、実行日時や実行環境（macOS, Linux, Windows）に依存せず、バイト単位で同一のテキストファイルを出力する。
- ファイルやルールの走査順序はすべて辞書順で安定ソート（Stable Sort）する。

### 4.5 ポータビリティとゼロロックイン (Zero Lock-in)
- `airch.yaml` は平易で直感的なYAML形式であり、ツール独自の難解なDSLやブラックボックスを排除する。
- 万が一 `airch` の利用を停止する場合でも、生成済みの `AGENTS.md` や `.cursorrules` はそのままスタンドアロンで利用可能であること。
